# typolish design: Versioning, decisions, stage plan

Part of the [typolish design](./README.md). Section numbers are those of the whole design.

## 15. Versioning, decisions, stage plan

### 15.1 Versioning and output stability

- The first release is `0.1.0`. SemVer as Cargo applies it: before 1.0 the second number is the
  breaking one. "A release that raises the breaking number" below means `0.1.x` → `0.2.0` before 1.0
  and `1.x.y` → `2.0.0` after it.
- API changes follow SemVer; the commitments of section 2.13 keep extensions additive.
- **Output changes.** The output of `PROSE` and `INTERFACE` for built-in languages changes only in a
  release that raises the breaking number (new rules in a set, changed lists, changed language
  data), with one exception: a patch release fixes output that contradicts this design, the README
  or the rustdoc, and records every such fix in the CHANGELOG with a "before → after" example.
  Output that matches the design but is wrong is a defect of the design; it is corrected in the
  design and in the code in a release that raises the breaking number. A new rule may arrive in any
  release, but outside both sets. This keeps the snapshots of build-time generators and the tests of
  callers stable across `cargo update` (settled in section 15.5, item 13).
- `RuleSet::ALL` and the base `all` of `RuleSet::from_str` mean every rule of the running version,
  so a rule added in any release joins them and their output may change with `cargo update`. Their
  rustdoc says so; callers who need stable output use `PROSE`, `INTERFACE` or an explicit list of
  rules (settled in section 15.5, item 13).
- A new built-in language arrives only in a release that raises the breaking number: its tag stops
  returning `Error::UnknownLanguage`, so callers that fall back to `Language::COMMON` get different
  output. It never changes output for tags that already resolve; the CHANGELOG lists the new tags
  (decided by the maintainer on 2026-11-22).
- MSRV: `rust-version` is raised only in a release that raises the breaking number, and the
  CHANGELOG says so; a dependency update that needs a newer Rust waits for such a release (decided
  by the maintainer on 2026-11-22).
- Rule ids are permanent (section 2.3).

### 15.2 Settled by the maintainer

Decided by the maintainer on 2026-11-21; not reopened here:

1. The crate is `typolish`, public on crates.io, independent of other projects; nothing is pushed or
   published without the maintainer's word (for the push, given on 2026-11-22: item 15).
2. There is no external corpus; the round trip is tested on the project's own corpus, and stage
   reports say so (sections 12.2, 13.7).
3. The reference implementation is installed only outside the repository. Its name appears nowhere
   in the repository (code, documentation including this design, commits, tests); the text says
   "reference implementation". Its pairs enter the tests as plain tables (section 13.4).
4. Git: the author is configured locally and is not changed; commits end with
   `Co-Authored-By: Claude <noreply@anthropic.com>`.
5. Dependency versions are the latest published, checked against crates.io, not memory (section
   14.1).
6. Rust 1.100 is both the MSRV and the installed toolchain; `rust-version = "1.100"` (section 14.4).
   MSRV policy: section 15.1 (decided by the maintainer on 2026-11-22).
7. License, authors and copyright exactly as in zonewright: `license = "MIT OR Apache-2.0"`, no
   `authors` field (zonewright has none), the license texts copied verbatim with the copyright line
   `Copyright (c) 2026 Dmitry Bikman`; only the year changes when needed (section 14.5).
8. Stages 2 to 5 run one after another after this design is approved (it was, on 2026-11-22: item
   15), without waiting for the maintainer between stages; the points of section 15.5 do not stop
   them (all of them were settled on 2026-11-22), and a decision received later is applied in the
   running stage, together with the change of the design, in the same commit. Stage 6 (HTML) is not
   done.
9. Working notes and Cargo's target directory live outside the repository.

Decided by the maintainer on 2026-11-22; not reopened here:

10. Every point of section 15.5 is settled with the option recorded there. Among them: the design is
    in American English (item 1); `repository = "https://github.com/dcl-group/typolish"` (item 2,
    section 14.5); the lead makes one query to the crates.io API in stage 5, which this decision
    allows, and none before (item 3, sections 1.1, 15.4); Russian numbers are grouped from four
    digits, `min_grouping_digits = 1` as in CLDR 49 (item 4, sections 2.7, 7.2).
11. A single initial before a surname is glued wherever it stands, also after a lowercase word that
    is not a short word (`сказал А.⍽Петров`). The cost, glue across a sentence end after a capital
    letter with a full stop (`вариант А.⍽После`, `plan B.⍽Then`, `did I.⍽Then`), is a known limit
    (sections 8.7, 10.8).
12. The MSRV is raised only in a release that raises the breaking number (sections 14.4, 15.1).
13. A new built-in language arrives only in a release that raises the breaking number (sections 2.2,
    7.7, 15.1).
14. `nbsp.dash` glues the space before every typed `–` with spaces between operands, numbers
    included: ru `10 – 20` → `10⍽– 20`, `Москва – столица` → `Москва⍽– столица` (sections 4.5, 8.7).
    This is approved behavior.
15. The design of version 0.1 is approved; stages 2 to 5 start (item 8, section 15.4). The
    repository is pushed to its remote once development is finished, after stage 5 meets its
    criteria (section 15.4), and not before; publishing on crates.io needs a separate word of the
    maintainer.
16. A compound word (a `Compound` core: letters or digits joined by single hyphens, `кто-то`,
    `tls-server`) is an ordinary word and operand for the dash rules and every other rule, not a
    technical fragment; only its hyphens are frozen, and no rule changes them. Its script is that of
    its letters: ru `кто-то - что-то` → `кто-то⍽— что-то`; Latin compound words in Russian text are
    foreign words, so ru `tls-server - agent-ca` stays (`AmbiguousHyphen`); in English text a dash
    between compound words follows the language's style, and `Closed` keeps the author's spaces next
    to a compound word, because a merge would give no valid fragment kind (invariant I2):
    `mother-in-law - father-in-law` → `mother-in-law — father-in-law` (sections 3.6, 8.2, 8.4,
    10.8).
17. `Number::decimal` accepts an optional leading `+` or `-`; a `+` is not written. Digits are kept
    as given, leading zeros and fraction digits included (`007` → `007`, ru `1.50` → `1,50`), and
    grouping applies to the integer part as written. A zero value is written without a sign, as for
    floats: `-0.00` → `0,00`, `Number::fixed(-0.001, 1)` → `0,0` (sections 2.7, 2.11).

Decided by the maintainer on 2026-11-23; not reopened here:

18. A particle is glued to the word before it, and a word glued backward as a particle does not glue
    the next word to itself: there is no chain. `Знаешь ли ты` → `Знаешь⍽ли ты`, not `Знаешь⍽ли⍽ты`
    (sections 7.2, 8.7; for every particle of the list: item 23).
19. A particle is glued to the word before it also when punctuation follows the particle: `Что ж,` →
    `Что⍽ж,` (sections 8.2, 8.7).
20. No glue sticks next to a fragment that holds an `Other` slot, not only next to the slot itself:
    `and "{o}"`, `в ({o})` and `и {d}{o}` keep their ordinary spaces (sections 2.6, 8.2; formerly
    the lead's choice C30).
21. Only `(` is an opening bracket for glue; `[` and `{` start technical notation, so `в [х]` keeps
    its ordinary space (sections 3.6, 8.2).
22. Initials between two capitalized words are glued to the surname after them, not to the word
    before: `Иван А.⍽Петров`, not `Иван⍽А. Петров` (section 8.7).
23. Item 18 holds for every particle of the list, not only `ли` that it names: a particle is glued
    to the word before it and glues nothing after itself, `Он⍽же пришёл`, `Я⍽б пошёл`,
    `Как⍽бы то⍽ни⍽было` (sections 7.2, 8.7; formerly the lead's choice C34).
24. Two particles in a row are both glued backward, each to the word before it: `что же бы ты` →
    `что⍽же⍽бы ты`, not `что⍽же бы ты` (section 8.7; formerly the lead's choice C33).
25. A bound particle glues nothing after itself also when `nbsp.particles` is disabled: the binding
    follows the particle list and its place, so with `nbsp.short-length` alone `Знаешь ли ты` stays
    unchanged (section 8.7; formerly the lead's choice C33).
26. A doubled sign stays as it is written: `Дело №№ 1, 2.` → `Дело №№⍽1, 2.`; the reference
    implementation merges it into one `№`, and the difference is deliberate (sections 8.7, 8.12).
27. The speed of the forward pass, about 7 to 15 MB/s on the corpus in Unicode output (6.8 to 14.6)
    against the indicative 20 MB/s of section 13.8, is accepted for version 0.1; the phases of
    section 3.8 are not reworked for it.
28. `to_plain` and `lint` cost about 100 to 200 times `typeset`, because every reading is checked by
    a forward run of the engine (section 12.1; formerly the lead's choice C31); this is accepted.
29. Every public item has a rustdoc example, every enum variant included; an example of the type
    does not stand for its variants (section 13.10).
30. `LanguageBuilder::abbreviations` takes entries made of parts and the way they bind; the list
    methods of `LanguageBuilder` replace the whole list, and `build()` rejects invalid data instead
    of repairing it (sections 7.1, 7.6; formerly the lead's choice C28).
31. The characters allowed for `minus_sign` are `-` and the dashes U+2010 to U+2015 and U+2212; the
    default stays U+2212 (sections 2.4, 2.11, 7.6; formerly the lead's choice C29).
32. Git history is not rewritten: the name of the reference implementation that old commits hold
    (split into parts, never whole) stays there, and `main` is never force-pushed (item 3, section
    14.7).
33. Code and tests refer to this design as "design section N.M" everywhere, never as a bare "section
    N.M". `design_references_say_design` in `tests/documentation.rs` checks the comments of every
    Rust file of the crate (section 13.10).
34. Publishing on crates.io waits for the maintainer's command; until then only the GitHub
    repository is pushed (items 1 and 15). The tag `v0.1.0` is set and pushed only on that command
    too (section 14.7).

The task itself fixes further points used throughout: the minus sign U+2212 for numbers, the
mandatory negative cases, HTML outside the core, `thiserror` for errors, `cargo deny check` clean,
clippy without warnings, rustdoc with an example on every public item, README and CHANGELOG in
English.

### 15.4 Stage plan

Every stage ends with a report: what was done, the list of commits, test results with output of
failures and of the comparison with the reference tables, what was not done or not verified, and
questions for the maintainer. In every stage the gates of section 14.7 pass before each commit, and
any deviation from this design is written into the design in the same change.

**Stage 2: core.** The stage starts by compiling the atom and token representation without
references (sections 3.4, 3.5, 2.12), because no check had compiled it (section 14.8); it was
compiled as the first code of the crate rather than in a scratch crate outside the repository. Then:
repository skeleton after zonewright (`AGENTS.md`, `CLAUDE.md`, README and CHANGELOG with an
